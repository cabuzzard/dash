# _content-governance (global method skill)

This is not a method you run on its own — every `make-*` skill in this repo (and any handoff
prompt generated by the dashboard's "Run skill" button) is governed by it. It defines the ONE
information flow that every asset must be produced through, and the ONE quality bar (voice)
every asset must clear before it's considered done. If a specific skill's own steps ever
conflict with this file, this file wins on research-sourcing and voice; the skill's own steps
still own format/structure/platform mechanics.

## The flow: Research governs everything downstream

```
Campaign Research  ─┐
Product fields      ─┼─► Product Strategy (positioning) ─► Pillar Content (per title) ─► Method-shaped Asset
Method framework    ─┘
```

Every stage **reshapes** the stage before it — it never invents new facts, and it never
re-paraphrases so heavily that the plain research language disappears. Two lossy
reformulations in a row (Strategy → pretty pillar essay → pretty-er slide copy) is how content
ends up "too clever" — abstract, generic-sounding, missing the actual specific benefit — even
though every individual step looked reasonable in isolation. The fix is discipline at every
step, not just the last one: pull phrasing from the nearest upstream source, close to
verbatim, rather than composing a fresh restatement of a restatement.

### Step 1 — Fetch the canonical Product Strategy record (not just any Strategy record)

The Strategy DB (`6f7a8666944746b2ae98d41db0c4e419`) has historically accumulated **duplicate
records for the same product** — a past bug let concurrent writes each create their own record,
so one product can have 2-4 Strategy pages, each holding a different subset of the 11 fields
(Customer, Niche, Pain Points, Emotions, Solution, Benefits, Unique Opportunity, Transformation,
Offer Structure, Proof Points, Objections). **Never just take `results[0]` from a query.**

Query the Strategy DB filtered by `Product` relation = this product AND `Method` is_empty
(that filter excludes legacy "Method Brief" rows, which are a different, older concept using
the same DB). If more than one result comes back, **pick the one with the most non-empty
fields filled in** — that's the real, complete record; the others are stale partial duplicates
from the same bug. Read all 11 fields from it, not just Benefits.

### Step 2 — Read the title's own Pillar Content section, if it has one

A Content Strategy title's page body may already carry a `### Pillar Content` heading_3
section — a ~800-1500 word piece composed from Campaign Research + Product fields + the
Strategy record above, written when the title was created. If present, **this is your primary
source material** — reshape it for this Method's format, don't recompose from the raw Strategy
fields yourself (that would just reintroduce the double-reformulation problem this file exists
to prevent). If a title has no Pillar Content section yet (older title, or this method's
creation path doesn't write one), fall back to Step 1's Strategy fields directly, plus Campaign
Research (Statement/Unique Opportunity/Key Message/Pain Points/Keywords) and the Product page's
own fields (Avatar/Transformation/Offer Structure/Proof Points/Objections/Unique Angle) as a
supplement — same discipline, just without a pillar essay as an intermediate layer.

### Step 3 — Read the Method's own framework page

Every method's Notion page body holds its actual voice/format rules (arc toolkits, structural
patterns, platform conventions, "Porting notes"/voice-fit corrections left by a prior
operator/agent pass). Read it before writing — it can override generic defaults below for this
one method specifically.

## The quality bar: voice fit is the FINAL check, after format fit, not instead of it

When a piece of copy has to be shortened, reworded, or compressed to fit a format constraint
(a Canva box, a headline word budget, a caption length cap, any tight field), the shortened
version must still **speak in the customer's own voice** — the register already established in
the Strategy record's Customer/Emotions/Pain Points fields (or Campaign Research's Target
Audience/Pain Points if no product is attached). It is not enough for a trimmed line to be
short and grammatically clean; it has to still sound like it's talking *to* the person reading
it, not describing a mechanism *about* them from the outside.

**The concrete failure mode to avoid:** a generated Hook headline read "When Your Workflow Runs
the Business" — fine, but too long for a template's tight Hook box. The instinctive fix under
space pressure was "The System Runs It." — three words shorter, grammatically clean, and it
genuinely fit the box. It was rejected: *"your title 'the system runs it' is nonsensical to the
customer — you have to write in the language OF the customer."* The actual fix, written by the
person the copy is for: "Save Yourself, Lean on Systems." — almost the same length, but it
addresses the reader directly ("yourself") and matches the emotional register the Strategy
record's own Customer/Emotions fields describe (overwhelmed, anxious about falling behind →
wants relief, confidence). "The System Runs It." describes a mechanism in third person with a
vague "it"; the fix speaks to a person. **Only the version that does both — fits the constraint
AND speaks to the reader — is acceptable.** If a shortened line doesn't do both, keep rewriting
it, don't just keep trimming it.

This applies to every piece of shortened/compressed copy in a deliverable, not just headlines —
kickers, captions squeezed to a character limit, CTA lines, footer labels, anything.

## Before finalizing any asset, self-check against this file

1. Does every specific claim/benefit/proof point in the output actually trace back to something
   in the Strategy record, Pillar Content, or Research — or did a "clever" reformulation drift
   into something generic that could apply to any product in this niche? If it's generic, it
   failed Step 1-2 above — go back to the source language and lift closer to it.
2. Does every line that had to be compressed to fit a constraint still address the reader in
   their own voice, per the section above — or does a short line quietly describe a mechanism
   in the third person instead of speaking to a person? If the latter, rewrite it, don't just
   accept it because it's short.
3. Report both the deliverable and, briefly, what it was grounded in (which Strategy fields,
   which Pillar Content, which Method framework notes) — so whoever reviews it can verify the
   grounding, not just take the output on faith.
