# Strategy Slots — dated changelog

Moved out of `CLAUDE.md` (2026-09-07 cleanup). `CLAUDE.md`'s "Strategy Slots and
Planning-stage titles" section keeps the load-bearing *rules*; these dated
paragraphs (the how-we-got-here) live here.

---

**Strategy Slots carry a `Type` and `Recurrence` (2026-08-24), distinct from Method/Platform.** Per operator direction: Method is really about platform/mechanics, but a Slot (and the title it produces) also needs a *strategic content category* — Teach/Take/Story/Relate/Thread/Reply, Free Teaser/Exclusive/Q&A/Livestream, whatever genuinely fits — that can carry more strategic information than Method alone and isn't tied to one platform. `generateGrowthStrategy`'s prompt now asks for a `type` and a `recurrence` (e.g. "Daily"/"Weekly"/"2x/week") per grouping, alongside the existing `recommendedMethod`/`recommendedPlatform`, and writes them onto every Slot it creates (`Type`/`Recurrence`, both rich_text, added to `STRATEGY_SLOTS_DB`'s schema). `generateTitleFromSlot` reads a filled slot's `Type` back out and both grounds the title-writing prompt in it ("CONTENT TYPE: ...") and copies it onto the created title's own new `Type` property (added to `CONTENT_STRATEGY_DB`) alongside the existing `Grouping` copy-through. A slot's `Status` still only tracks Open/Filled and its `Title` relation still only appends (never replaces) on each fill — the `Recurrence` value doesn't change that state machine, it's descriptive metadata for a human (or a future daily-readout/recurring-To-Do feature) to act on by re-triggering `generateTitleFromSlot` on an already-Filled slot when its cadence comes due; nothing auto-fires yet.

**Live Grok (`api.x.ai`) grounding for X titles, at the point they're actually written.** `generateTitleFromSlot` calls `callGrokTrendingTopics` (plain `fetch()` to xAI's OpenAI-compatible chat-completions endpoint, model `grok-4.6` — not MCP, the Worker has no MCP client) whenever a slot's `Platform` matches X/Twitter, grounded in the product's own Niche/Customer from Product Research. Best-effort and silent-safe: returns `""` (no-op, logged via `console.error` on real failure so it's visible in `wrangler tail`) when `XAI_API_KEY` isn't set. This is deliberately at *fill* time, not Growth Strategy planning time — a Slot can sit Open for weeks before being filled (especially a recurring one), so pulling live trends when the title is actually written keeps it current in a way baking trends into the upstream strategy plan wouldn't. Requires the `XAI_API_KEY` Worker secret (`wrangler secret put XAI_API_KEY`, from an xAI Console key).

An earlier version of this lived in `generateTrafficMethodTitles` — that action had no UI caller and was removed once this capability was rebuilt here, in the actual live path.

**`runStrategySequenceReminders` — the nightly "what's next" queue (2026-08-24).** Runs in `scheduled()` on the existing `0 0 * * *` daily cron, alongside `runListingRepostReminders`. Content Strategy gained a dual `Strategy Slot` relation (paired with Strategy Slots' `Title`) so a published title can trace back to the Slot that produced it — `generateTitleFromSlot` sets this on every title it creates from a slot. Each run: pulls every Published title with a `Strategy Slot` set, groups them into "lines" (same Growth Strategy + Grouping), and per line finds the most recently published title and reads its Slot's `Type`/`Sequence`/`Recurrence`. Sequential lines (a `Sequence` number set) get the next sibling Slot at `Sequence + 1` that's still Open; Recurring lines (a `Recurrence` phrase, no more sequential slots) re-fire the *same* Slot once its interval has elapsed since the last publish — Slots already support being filled more than once. Writes exactly one Main TD item per active line via a new `Strategy Slot` relation on `MAIN_TD_DB` itself; idempotent by re-derivation each night rather than event-triggered off any of the 20+ places Asset Status gets set to Publish — a stale TD (pointing at a Slot no longer correct for its line) gets archived (`{archived: true}`, real Notion delete) and replaced, a correct one is left alone, nothing gets created before its due date. (See also `docs/strategy-sequence-next.md`.)

**Deliberately out of scope so far:** the third bucket from the operator's design — "maintenance, not new content" (e.g. an Etsy listing that just needs periodic reposting) — is `runListingRepostReminders`, a separate, older mechanism, not folded into this. **Legacy published content has no Strategy Slot and is invisible to this scan** until it's retroactively backfilled with one — that backfill (reverse-engineering a Slot for everything published before this system existed, reusing the Posting-Cadence-artifact-style grouping) has not been built yet. Nothing here auto-publishes anything — it only queues a To-Do; the operator's own stated long-term/aspirational idea of a cron job that runs actual publications is explicitly not attempted yet.

**`runListingRepostReminders` moved onto the Weekly Planner (2026-09-04).** Per operator direction ("the listing reposts need to go onto the weekly schedule under TD, with a day of the week quality added to them"), this stopped writing one-off `MAIN_TD_DB` items on a manually-tracked "Last Repost Reminder" 7-day clock on the Asset. It now creates exactly one **`WEEKLY_PLANNER_DB`** row per Published `listing` Asset — idempotent via a new `Source Asset` relation (Weekly Planner → Assets) so a listing never gets a second row — with `Source: "Listing Repost"` (new select option) and `Date` set to today (the day it's first seen Published). Weekly Planner's own existing recurrence machinery (`wpFetchProjectedItems`: an Open row's `Date` anchors its weekday and the row re-projects onto every future week automatically) does the actual weekly repeat — this function no longer tracks its own interval at all, it just guarantees the row exists. The "Last Repost Reminder" date property on `ASSETS_DB` is now dead (left in place, unused, rather than dropped).

**🏷️ Post Types — standalone global taxonomy of content descriptors (2026-08-27), distinct from Sequence/Recurrence (timing) and from the free-text `Type` field.** A new database (`POST_TYPES_DB`, Name + Rationale) holds a curated, operator-grown list of WHAT KIND of content a slot is — Pillar, Intro, Character Development, Feature Benefit, CTA, Teach, Story, Behind-the-Scenes, Q&A, Announcement, Social Proof. **Not** cadence/timing — that's `Sequence` (position in an ordered series) and `Recurrence` (how often, e.g. "Weekly"), both unchanged and orthogonal. (First seeded 2026-08-27 from Content Strategy's legacy `Post Type` select, which actually held cadence values (Sequential/Recurring/One-off/sm post) — that was a same-session misread, corrected before any real data referenced it; those entries got renamed into real content descriptors instead of left dangling.) Strategy Slots gained two relation properties: `Post Type` (→ `POST_TYPES_DB`) and `Platforms` (→ the existing `PLATFORMS_DB`, distinct from the older free-text `Platform`).

`generateGrowthStrategy` assigns a Post Type to **every individual title**, not once per grouping — its `groupings[].titles` are now `{angle, postType, newPostType}` objects, not plain strings. The prompt is handed the full Post Types catalog (Name + Rationale) and told to vary the type across a Sequential grouping's titles to match their position in the arc (Intro → Character Development → Feature Benefit → CTA, grounded in the actual product/research/campaign context already in the prompt — never a generic template), or reuse one/cycle 2-3 for a Recurring or one-off grouping with no real arc. **Every strategy must include at least one Pillar title** — the anchor everything else drives traffic to — per operator direction ("if you did away with all strategy and wrote one sales page for a product, it would start with the pillar being that"). A title can flag `newPostType: true` to create a genuinely new catalog entry on the fly (rare; prefer reuse) — `resolvePostTypeId` in `generateGrowthStrategy` handles matching/creating and dedupes new names within one call. `Platforms` still resolves via grouping-level best-effort name match (`recommendedPlatform` vs `PLATFORMS_DB`, unchanged from Post Type's original single-per-grouping design — Platform is genuinely a per-grouping property, Post Type is not).

**Slot naming convention: `"{sequence} – {Post Type name}"`** (e.g. `"3 – Feature Benefit"`) — set at creation and kept in sync by `removeStrategySlot`/`insertStrategySlot` (`renumberedSlotName` only rewrites names that already match the pattern; older/manual names are left alone).

The microsite's Strategies panel titles each slot row by its Post Type (Rationale as a native tooltip) instead of the slot's raw Name, so a grouping's slots read as the strategy's *arc* at a glance. A **✏️ Edit Slot** button opens a modal (`editSlotModal`) to change the Proposed Title (Angle), Post Type, or Best Platform(s) directly — each picker supports search-existing-or-create-new inline (`createPostType`/`createPlatform`, mirroring the Login platform picker's autocomplete+create convention). A **🗑️** button and a thin **"+ insert"** row above every sequenced slot (plus one trailing) call `removeStrategySlot`/`insertStrategySlot` — per operator direction, adding or removing a slot mid-sequence renumbers (and, where the name still matches the convention, renames) every later sibling in the same Growth Strategy + Grouping, so the sequence stays contiguous. New worker actions: `getPostTypes`, `createPostType`, `updateStrategySlot`, `removeStrategySlot`, `insertStrategySlot` (`getPlatforms`/`createPlatform` already existed). Deliberately independent of Method for now, per operator direction — no Post Type → Method mapping exists yet.

**Offer asset type (2026-09-01).** A direct-sales asset: one Product → one finished, published **Offer**, presented the way it appears on a content hub / sales page (not N concept options). It is **a method like any other** — the `Offer` method (`METHODS_DB`, Status Live, Category Content+Ecommerce) shows up in the Generate Assets modal's method picker (`searchMethods`, all Live methods), and `gaAutoAttachMethod` attaches it to the campaign on generate. No hard-grind change was needed: a plain method with no `GA_SKILL_METHODS` entry falls through to the generic path where `assetType = GA_METHOD_NAME` ("Offer"), and `generateTitleAssets` has a new `/\boffers?\b/i` branch (worker.js, sits next to the SEO Post / LinkedIn Post branches) that: requires a product; grounds a single Claude call in the product's 🔬 Product Research (`STRATEGY_FIELDS`) + the Product page fields (Description / Transformation / Offer Structure / Price / `URL` / Unique Angle / Product Tier) + campaign Key Message/Pain Points/Target Audience + the Method's own page-body framework; creates ONE Asset (Type "Offer", Status Publish, `Content URL` = the product URL, `Platform Title` = the offer name); writes the page body starting with a fenced `json` **OFFER CARD** block (`{kicker, name, promise, ctaLabel, ctaUrl}` — for a later hub-publish step to read verbatim into a `{kicker,title,excerpt,url}` card) then the pitch (For who / What's included / Why it works / The objection it answers / Terms / CTA); and sets the source title to Publish. The intended pipeline: Product (in an *Offers* Product Stack, Product Tier = ladder rung) → Product Research → Title (Post Type **Direct Sales** — new `POST_TYPES_DB` entry) → Offer method → Asset → the campaign's content hub.

**Offer split into two methods (2026-09-02).** The `Offer` method was renamed **`Offer – Pillar`** (the research-grounded sales-page version above, unchanged) and a sibling **`Offer – Content Hub`** method added (`METHODS_DB`, Live, Content+Ecommerce). Both match the same `/\boffers?\b/i` branch (assetType = method name). Naming convention: `Offer – <variant>`.
- **`Offer – Content Hub`** is zero-research — the offer branch already degrades gracefully without a 🔬 Product Research record, so it runs off the Product page fields + campaign + the title's pillar. Built for the **`Site Ideas`** product stack: ~47 products bulk-created 2026-09-02 from the 8 hubs' hand-written `HUB.trips.items` (Name + Description = card blurb + Notes = provenance; Campaign relation; no research/status/methods). `ai-implementation` (9) + `care-gap` (4) of those are really topic/program cards, not products.
- The offer branch now also sets a **`Product`** relation on the asset (new ASSETS_DB property, one-way → Products). ASSETS_DB also gained **`Content Hub`** (select, the 8 hub slugs).
- **The hub Products section is now live** (`web/hub/hub-template.html` + all 8 hub files): `renderHubProducts()` replaces the static `renderCards(HUB.trips…)` call — fetches `getHubProducts` (public worker action: campaign's published `Offer – Content Hub` assets whose `Content Hub` = this slug or unset, each parsed from its `OFFER CARD` block into `{kicker,title,excerpt,url}`), falls back to the hand-written `HUB.trips.items` when nothing's published. Exact `renderNews`/`getHubNews` pattern.
- **The hub is chosen at publish time.** The Publish modal (hard-grind + `sync_microsites.py` → 37 sites) shows a conditional **Content Hub `<select>`** for `Offer – Content Hub` assets (`pubHubWrap`), populated from `getContentHubs` (public, returns the worker-side `HUB_SITES` constant — slug/name/campaignId, keep in sync with index.html) filtered to the microsite's `CAMPAIGN_ID`, saved via `updatePublishFields` (`contentHub`, validated against `HUB_SITES`). `getTitles` asset summaries carry `contentHub`.

**`deleteGrowthStrategy` (2026-08-27)** — a 🗑️ **Delete Strategy** button on every strategy header (flat, divergent parent, and each child individually). Real Notion archive, cascading sensibly rather than leaving orphans: a divergent parent's children get deleted with it (they have no independent existence without the parent); every Strategy Slot under any deleted strategy is archived; any real title that pointed at a deleted strategy/slot is never deleted, only unlinked (`Growth Strategy`/`Strategy Slot` relations cleared) so it survives and just drops back into Unassigned Planning Titles instead of the panel silently losing track of it.

**Guides and Runs (`launchStrategyRun`, 2026-08-27).** Per operator direction: a strategy can act as a reusable **Guide** — the content framework (groupings, angles, recommended Method/Platform per grouping) — that stays in the Strategies panel, while an actual execution against a specific Product is a **Run**. Implemented by reusing the existing divergent-path Parent Strategy relationship rather than a new DB: a Run is just a Growth Strategy child (`Parent Strategy` = the Guide), which every existing piece of strategy machinery (rendering, `backfillStrategyPostTypes`, `deleteGrowthStrategy`'s cascade) already understands with zero changes. ANY existing strategy can serve as a Guide, not only ones with no Product of their own. A **🚀 Launch Run** button on every strategy header opens a small modal (pick a Product) and calls `launchStrategyRun(guideStrategyId, productId, campaignId)`, which: parses the Guide's own page body back out (the inverse of `generateGrowthStrategy`'s `groupingBlocks()` — each `heading_3` is a grouping name, the paragraph after it the rationale, `bulleted_list_item`s the angles, the bold "Method: X · Platform: Y" paragraph the recommendation), creates the child strategy, then bulk-creates that Run's own fresh Strategy Slots (Sequence/Angle/Method Name/Platform) for the chosen Product — reusing the Guide's content without regenerating it via AI. Post Type is deliberately left unset on a Run's new slots (no reliable per-grouping mapping to copy without another AI call) — the existing 🏷️ Assign Types button is the already-built way to fill it in after. Verified end-to-end against a real Guide (Tool Guides → a CRM-product Run: 6 groupings, 30 slots, angles/method/platform all correctly parsed) before this was committed.

**`backfillStrategyPostTypes`** retroactively assigns Post Type to an existing Growth Strategy's slots that don't have one — same research-grounded reasoning as `generateGrowthStrategy` (re-fetches the strategy's own Product/Positioning/Campaign Research context), never touches Angle/titles. A **🏷️ Assign Types** button appears on any strategy in the microsite panel that has at least one untyped slot. Covers the 147 pre-existing slots from before this rework existed, and any future gaps.

**Correction, 2026-08-27 — Method removed from Growth Strategy generation entirely.** The `recommendedMethod`/`newMethod`/`newMethodCategory` fields (and the method-catalog grounding/attach loop they drove) and every `"Method Name"` write onto a Strategy Slot (both in `generateGrowthStrategy`'s `createSlotsFor` and in `launchStrategyRun`'s Run-slot creation) have been removed. Per operator direction: *"dont worry about method. I choose method or create new when I make titles. there shouldnt be mthod in slots. slots just have a platfrom."* A Strategy Slot now carries **Platform only** (plus Post Type) — Method is chosen exclusively at title/asset-creation time, same as [[feedback_dash_methods_pull_not_add]] already established for the manual-add case. `groupingBlocks()`'s body-prose paragraph dropped its "Method: X · " prefix, now just "Platform: Y" — `launchStrategyRun`'s block parser still tolerates the old "Method: X · Platform: Y" format from pre-existing Guides (regex unchanged), it just no longer writes Method onto anything it creates. `generateGrowthStrategy`'s `attachedMethods` return field is kept as an always-empty array so the existing UI status note degrades silently rather than needing its own change. Verified live building the "AI Audit - Ad Support" strategy for the AI Business Audit product (5 groupings across Instagram/LinkedIn/Facebook, divergent-split into a parent + 5 child strategies as designed) — one grouping ("Tool Stack Teardowns") came back from the AI with zero titles, backfilled manually via 5 `insertStrategySlot` calls after the fix deployed, confirmed via a live `getCampaignGrowthStrategies` read to carry Platform/Post Type but no Method.

**Weekly Planner cards — traffic-light flag + drag-to-reorder (2026-09-09).** Per operator direction ("drag to re order and red yellow green highlightint on the weekly td items … red urgent, green done, yellow planning, set onclick … all weekly views, when done in one place transfers to the other"). Both surfaces (root `index.html` This Week board + the microsite `hard-grind` template → `sync_microsites.py` → 37 sites) read the same `WEEKLY_PLANNER_DB` rows, so state transfers automatically.
- **New `Flag` select** on `WEEKLY_PLANNER_DB` (`Urgent`:red, `Planning`:yellow). A round dot on each card cycles none → 🔴 Urgent → 🟡 Planning → 🟢 Done → clear; the card gets a matching 3px left border. Green is *not* a stored Flag option — it mirrors `Status: Done`, so the "done" end of the cycle sets `Status: Done` (+ stamps today's Date, like `completeWeeklyPlannerItem`) and the next click reopens + clears. Worker action `setWeeklyPlannerItemFlag {itemId, flag}` where flag ∈ `Urgent`|`Planning`|`Done`|`None`. `wpFetchProjectedItems`' `mapRow` now returns `flag`.
- **Drop ONTO a card** = reorder within (or into) that card's day — top half above the target, bottom half below. Worker action `reorderWeeklyPlannerItems {orderedIds, day}` renumbers the whole day's `Order` (0..n) and pins every listed row's `Date` to that weekday (so a card dragged in from another day lands there, matching `moveWeeklyPlannerItem`). Dropping on the empty day area still calls the old `moveWeeklyPlannerItem` (append to end). Frontend: `wpItemDragOver`/`wpItemDrop`/`wpCycleFlag` (root) and the `WP_DRAG_ID`/`WP_ITEMS_CACHE` equivalents (microsite).
